Other registered product modules include member courses and indicators, trading rooms, watchlists, boards, and orders. Their boundaries and dependency graphs still need classification; this inventory does not treat each product directory as a reusable plugin by default.

## Extraction architecture

1. Finish the runtime contract audit for each system: registered HTTP routes, response schemas, persistence, browser mount points, authorization, consent, and failure behavior. Record unsupported UI options rather than silently simulating success.
2. Add a disposable end-to-end fixture per system. Test both successful and failed writes, authorization, data retention, and a browser flow. Keep production credentials out of test fixtures.
3. Define a package boundary: framework-neutral core for validation and policy, adapters for SvelteKit/Axum/PostgreSQL/Redis/storage, explicit configuration, versioned migrations, and an install guide. Do not copy the whole application into a package.
4. Package one system at a time in its own workspace directory with named exports, peer dependency ranges, example integration, compatibility matrix, changelog, and automated release checks. Begin with forms, popups, and consent once their remaining endpoints are reconciled.
5. Measure latency, payload size, database load, and cache hit rates before and after changes. Use bounded Redis caching for read-heavy data only with mutation invalidation and short expiry; consent decisions and writes must remain authoritative.
6. Gate release on the repository checks, disposable database/browser tests, dependency and security review, accessibility, and installation into a separate example app. Validate the actual Fly.io/Cloudflare deployment after its target is known.

## Evidence from this audit

- `api/tests/marketing_plugins_integration_test.rs` runs against an **empty** local database named `marketing_verify*` and drives the real router.
- `frontend/tests/marketing-runtime.spec.ts` drives the consent and popup browser flow with an intercepted campaign API response.
- `frontend/src/lib/api/forms-contract.test.ts` and `popup-contract.test.ts` check the Rust/frontend DTO boundaries.
- `frontend/src/lib/consent/templates/registry-contrast.test.ts` checks solid accept-button colors against the 4.5:1 text contrast threshold. The existing browser axe gate now passes on all sampled marketing routes.
- `frontend/tests/admin/behavior.spec.ts` passed both Chromium flows against the local disposable Rust API: ingested events appeared in the admin heatmap/session UI, and analytics consent started tracking while withdrawal stopped it.
- The existing no-database `forms_test.rs`, `popups_test.rs`, and `consent_test.rs` are useful contract tests but do not prove persistence or a browser flow.
- The local SEO gate passes 111/114; its remaining sitemap/content tests depend on a running local content API.
- On 2026-11-07, the Cloudflare Pages main `/about` route served the merged client assets and a fresh Chromium session showed the consent dialog. Rejection made zero popup lookups and left cookie settings available. After acceptance, `/api/popups/active` returned HTTP 307 to `/maintenance`; a public API deployment remains a live end-to-end gate.

No result here establishes a production API deployment, universal compatibility, or superiority to a commercial product. Those require measured comparisons and separate installation tests for the remaining embedded systems.
